# Журнал решений

## 2026-10-17 13:10:49 UTC — Каркас репозитория

Стек уже выбран в `docs/TASK.md`: Django и Django REST Framework, Channels, Celery и Redis, PostgreSQL, React на Vite, почта-заглушка, один репозиторий с `backend/` и `frontend/`, запуск через Docker Compose. На этом шаге добавлен только каркас, без доменной логики.

Backend — проект `config` и приложения по границам продукта:

- `accounts` — профиль водителя, почта, номера машин, вход
- `parking` — схема и места; сюда же встанет WebSocket занятости
- `bookings` — брони; сюда же встанет снятие брони, если за 15 минут не было заезда
- `visits` — заезд, выезд и счёт за визит
- `tariffs` — дневной и ночной тариф по минутам
- `gate` — симулятор шлагбаума
- `notifications` — письмо за 10 минут до конца брони

Так следующий шаг можно делать внутри одного приложения, не смешивая тариф, бронь и шлагбаум. Одно общее приложение было бы короче, но эти правила пересекаются и их проще держать отдельно.

Зависимости backend перечислены в `backend/requirements/base.txt` и пока без закреплённых версий: Django, djangorestframework, channels, channels-redis, celery, redis, psycopg, daphne. Daphne — ASGI-сервер, без которого Channels не принимает HTTP и WebSocket в контейнере. `channels-redis` нужен, чтобы два клиента видели одну и ту же занятость через Redis. Отдельный пакет вроде django-environ не добавлялся: настройки читаются из окружения стандартной библиотекой.

Почта: в Compose есть Mailpit, а `EMAIL_BACKEND` по умолчанию консольный. Так письма можно смотреть и без SMTP. Переключение на Mailpit — переменной окружения, когда появится задача отправки.

Frontend — Vite и каталоги `src/features/` с теми же границами: схема, брони, шлагбаум, визиты, профиль. Состояние экранов общее пока не заведено.

Альтернатива, которую не взяли: сразу поднимать рабочий `docker compose` и ставить пакеты. Сначала зафиксирован каркас, чтобы зависимости и миграции попали в отдельный шаг, когда их можно проверить.

## 2026-10-17 13:53:20 UTC — Модели и ограничения в PostgreSQL

Схема без API и без правил заезда. Деньги — целые копейки (`PositiveIntegerField`), моменты времени — `timestamptz` в UTC (`USE_TZ`).

Активные брони одного места не пересекаются ограничением `EXCLUDE USING gist` по месту и `tstzrange(starts_at, ends_at, '[)')`. Для равенства по целому ключу места нужно расширение `btree_gist`. Интервал полуоткрытый: бронь, которая заканчивается в T, не мешает брони с T. Ограничение действует только при `status = active`, поэтому отменённая бронь место не держит. Проверка только в приложении этот зазор между двумя одновременными вставками не закрывает.

Активный визит — строка с пустым `exited_at`. Частичный уникальный индекс по `plate` не даёт одному номеру два таких визита. Выехавший номер можно записать снова.

Тариф — строка с `effective_from`, а не константа в настройках: смена ставки должна оставаться в истории. Дневная и ночная ставки и их границы лежат в одной строке. Часовой пояс парковки — поле этой строки (имя IANA), сами границы — локальное время суток. Какой пояс и какие часы включить, ещё не выбрано, поэтому строк тарифа нет.

Состояние места на схеме не хранится: его дадут брони и визиты. У шлагбаума своей таблицы нет, заезд и выезд — это визит. Напоминание — одна строка на бронь (`OneToOne`), отправка письма ещё не сделана. Водитель не связан с учётной записью Django: модель входа открыта. Номер на брони и визите — текст как есть, без нормализации; глобально уникальным он не сделан, потому что вопрос «один номер у нескольких водителей» открыт.

`django.contrib.postgres` входит в Django, отдельный пакет не добавлялся. Выражения `TsTzRange` в Django 6.1.2 нет, диапазон для ограничения собирает локальный `Func`.

## 2026-10-17 14:13:59 UTC — Место визита, номер, счёт и статусы брони

У активного визита (`exited_at` пустой) два частичных уникальных индекса: по номеру и по месту. Иначе два заезда без брони могли занять одно место. Выехавший визит оба индекса отпускает.

Номер перед записью приводится к одному виду, и индекс стоит уже на нём. Правило: верхний регистр, без пробелов и дефисов, кириллические буквы номера (А В Е К М Н О Р С Т У Х) складываются в латинские двойники. Поэтому `a 123 bc` и `А123ВС` — одна машина. Хранить «как есть» нельзя: двойной заезд обошёл бы индекс. Может ли один номер быть у нескольких водителей, по-прежнему не решено.

Счёт — таблица `Invoice`, одна строка на визит (`OneToOne`), сумма в копейках и время выставления. У визита nullable-ссылка на бронь: заезд без брони её не заполняет. Поля суммы на визите убраны, чтобы история счетов была отдельным списком. Разбивки по дневным и ночным минутам в схеме ещё нет.

`ends_at > starts_at` уже было ограничением `booking_ends_after_start`, его оставили. Статусы брони: `active` держит место в exclusion; `cancelled` — снята до использования; `expired` — не заехали, бронь больше место не держит (снятие через 15 минут ещё не сделано); `completed` — заезд по брони состоялся. Переходы между ними — не этот шаг. Неизвестное значение статуса база не примет.

## 2026-10-17 14:50:13 UTC — Правила парковки в схеме

Логики заезда и API нет. Ниже то, что теперь видно в базе, и правила, которые база не проверяет, потому что они зависят от «сейчас».

Тариф — строка с `effective_from` 2020-01-01 00:00 UTC, пояс `Asia/Bishkek`, день 07:00–23:00 по 200 копеек за минуту, ночь 23:00–07:00 по 100. Границы — локальное время этого пояса. Считаются начатые минуты: `ceil(секунды / 60)`. Ставка минуты берётся по моменту её начала. Нулевая длительность стоит 0. Бронь бесплатна, оплачивается стоянка по факту, счёт по-прежнему `Invoice`. Расчёт в код не переносился.

Место на схеме «забронировано», когда активная бронь покрывает текущий момент и визита по ней ещё нет. Отдельной колонки состояния нет.

Заезд по брони возможен только в окне от `starts_at` до `starts_at` + 15 минут. Раньше начала это заезд без брони. После окна бронь подлежит статусу `expired`. Заезд без брони берёт место, где нет активного визита и нет активной брони, пересекающей ближайшие 15 минут; иначе ответ 409. Если забронированное место уже занято визитом, выдаётся другое свободное по тем же правилам, иначе 409. Задержка сверх конца брони не ограничена, счёт по фактическому визиту. Эти ветки не написаны.

Длительность брони в базе от 15 минут до 24 часов включительно (`booking_duration_15m_to_24h`). «Начало не в прошлом» чек-ограничением не сделать: строка, верная в момент создания, позже оказывается в прошлом. Это проверка при создании брони, её ещё нет.

Статусы: `active` (место держится, заезда не было), `checked_in` (заехал), `completed` (выехал), `cancelled`, `expired` (не заехали в окно 15 минут). В exclusion входят `active` и `checked_in`. Отмена, просрочка и завершение место для других броней не держат.

Нормализованный номер уникален среди машин глобально. У водителя может быть несколько номеров. Бронь ссылается на `Vehicle`, а не на произвольный текст, поэтому номер брони всегда чей-то. Проверка «этот водитель бронирует именно свою машину» — при создании брони, не в этом шаге. Заезд с неизвестным номером допустим: у визита `driver` nullable.

Вход — email и пароль пользователя Django и токен DRF (`rest_framework.authtoken`, отдельный пакет не добавлялся). `Driver` — `OneToOne` к пользователю, почта профиля — `User.email`. Встроенный `User` требует `username`, туда пишется тот же email. Повторяющийся непустой email запрещён частичным уникальным индексом. Свой `AUTH_USER_MODEL` не вводился: таблицы auth уже созданы.

Письмо одно, за 10 минут до конца брони. У напоминания одна строка на бронь, `sent_at` пустой, пока письмо не забрано. Перед отправкой строка помечается атомарно: `UPDATE ... SET sent_at = now() WHERE booking_id = ? AND sent_at IS NULL`. Ноль обновлённых строк — письмо не отправлять. Сама отправка не сделана.

## 2026-10-17 15:14:16 UTC — Свой пользователь с почтой вместо username

Проект ещё пустой, база поднимается заново через `docker compose down -v`, поэтому `AUTH_USER_MODEL = "accounts.User"` заведён сейчас. Вход по email: `USERNAME_FIELD = "email"`, поля `username` нет. Прежняя причина «таблицы auth уже созданы» больше не действует.

Почта — `EmailField`. Формат проверяет валидатор поля, не сырой SQL. Менеджер при создании приводит адрес к нижнему регистру и обрезает пробелы; `save()` делает то же, чтобы в базе не осталась смешанная запись. Уникальность без учёта регистра — `UniqueConstraint(Lower("email"))`. Рядом стоит `unique=True`: Django не принимает `USERNAME_FIELD` без уникальности самого поля (`auth.E003`). `RunSQL`, триггер и запись email в `username` убраны, миграции собраны заново.

`Driver` — `OneToOne` к `settings.AUTH_USER_MODEL`. Токены по-прежнему `rest_framework.authtoken`. Регистрация создаёт пользователя, профиль водителя и токен. Вход ищет пользователя по уже нормализованной почте и возвращает тот же токен.
